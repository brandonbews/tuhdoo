# tuhdoo — Technology Decisions

**Date:** 2026-07-29
**Status:** Cycle 2 grilling outcomes. Builds on `001-core-design.md`; where the two touch, this doc is the more specific authority and `001` carries a revision note.

---

## T1. Daemon language: Go

The daemon is written in Go. Criteria, ranked for the agentic era (agents write most code; the human steers by reviewing): **distribution** (single static binary per platform — `brew install tuhdoo` with zero runtime dependency is the strongest v0 install story), **reviewability by the steering human** (Go is designed to be read by people who didn't write it; the author is a TS dev deliberately learning Go, and review-reading ramps far faster than writing), **agent competence** (large corpus, agents write it well), **ecosystem** (official MCP Go SDK; best-in-class TUI ecosystem — see T7).

- TypeScript was the real rival (MCP's first-class citizen, author's home language, one language with a future web UI) and lost narrowly on install story and daemon-grade auditability.
- Rust dismissed for this phase: hardest for the author to review, slowest to iterate, and v0's problem is product discovery, not performance.

**Accepted risk:** the author's steering power is reduced for the first weeks of Go reading. Mitigations, adopted as project law:

1. **Boring Go only.** Written convention: no clever concurrency (no channels-of-channels, no sync gymnastics); plain mutexes, plain loops — code a learner can audit.
2. **The deterministic core is pure functions.** Replay, winner rules, lease expiry, compaction, and view generation take data in and return data out — no I/O — and carry table-driven tests ("this event set produces exactly this state/bytes"). Correctness rests on reviewable tests, not line-by-line vigilance.

## T2. Git access: subprocess plumbing, no checkout, app-level merges

- **Subprocess `git`** (not go-git, not libgit2 bindings, not Dolt-style): fetch/push inherit the user's entire auth reality (SSH agents, credential helpers, `gh` tokens, proxies) for free, and the daemon takes no third-party correctness risk on the one job that must never corrupt data. go-git's auth story and long-tail correctness gaps disqualify it; libgit2 Go bindings are unmaintained; Dolt-style (beads' `refs/dolt/data`) pays a heavy dependency and loses host-browsability to buy cell-level merges our event log doesn't need.
- **The data branch is never checked out.** Writes use plumbing: `hash-object` → `mktree` → `commit-tree` → atomic `update-ref`. Reads use `cat-file` / `ls-tree`. No worktree, ever.
- **Merges are application logic, not git machinery.** Divergent data-branch histories merge by set-union of event files + deterministic view regeneration; the daemon computes the merged tree itself and writes a two-parent merge commit via `commit-tree`. `git merge`, conflict markers, and merge drivers are never invoked.
- The daemon operates **directly on the user's `.git`** (shared object store, atomic ref updates, tuhdoo-owned refs) — no shadow clone.
- The data lives at a **normal visible branch** (`refs/heads/tuhdoo`), not a hidden custom ref — host browsability (D4) requires it.
- All git access goes through a small internal `Git` interface so a library could slot in later without a rewrite. Minimum supported git version documented (target: ≥ 2.40).

**Host-agnostic by construction (named constraint).** tuhdoo speaks the git protocol and nothing else: any remote works (GitHub, GitLab, Bitbucket, Gitea, a bare repo on a NAS or USB drive), and **no remote** works too — absent a remote, the sync loop simply doesn't run and everything else is fully live; adding a remote later is detected automatically and the first push publishes the branch, no migration. The daemon never calls a host API; Run→PR links are stored strings, never dereferenced. Host-specific features (issue-intake bridges, webhook-driven fetch) are forever optional add-ons, never core. `tuhdoo init` must not assume a remote; `status` shows `local-only` as a normal state, not an error.

## T3. Event format: canonical JSON, versioned envelope, fail-safe degradation

**Serialization.** One event = one file (mutable shared files like JSONL conflict; settled by D3). Format: **JSON in a canonical encoding** — sorted keys, fixed number/string forms, UTF-8, no insignificant whitespace. Canonical bytes are what make the reserved `sig` field possible later and make identical events produce identical bytes everywhere. Filename = event ID: `events/2026/07/29/<ULID>.json`.

**Envelope** (every event, regardless of type):

```json
{
  "id": "01J9GQ3V7R8Z4M2K...",        // ULID — sole ordering key
  "type": "task.created",             // noun.verb, namespaced
  "v": 1,                             // schema version OF THIS TYPE
  "actor": "brandon/impl-2",          // D7 principal
  "machine": "m-3f9a",                // stable per-machine id
  "task": "t-01J9GQ...",              // subject task, if any
  "sig": null,                        // reserved (D7)
  "data": { ... }                     // type-specific payload
}
```

**Ordering.** Replay order is ULID lexical order — a deterministic total order whether or not wall clocks are truthful. A skewed clock can make a claim unfairly win "earliest"; it can never make two machines disagree about who won. Fairness-under-skew is traded for mandatory determinism. No Lamport machinery in v1.

**The three version contracts** (distinct, independently moving — conflating them is how tools nag users into constant upgrades):

| Contract | Bumped when | Consequence of mismatch |
|---|---|---|
| **Event schema** (per-type `v`) | Breaking payload change only — additive fields never bump it | **Fail-safe mode** (below). Rare by design; ideally major versions only. |
| **View format** (single integer) | Rendered markdown output changes | Cosmetic: older machines see slightly stale markdown until upgrade or peer sync (T6). No lockout, no nag. |
| **Daemon binary** | Every release | None. Peers at different binary versions collaborate in total peace if the above two match. |

**Versioning rules:** additive-first (readers ignore unknown fields; rewriters preserve them); breaking changes bump per-type `v` and the daemon carries **upcasters** — pure functions lifting old shapes to current at replay time, in memory only; stored bytes are never rewritten.

*Clarified 2026-07-31 (inbox/held statuses — the first real bump):* "additive" means an old reader that ignores the new field still computes **correct** state. A field whose absence implied a default that its presence can contradict is a breaking change in additive clothing: verified empirically, a v1-only binary decoding a `task.created` that carried `status: "inbox"` dropped the unknown field and minted the task open-and-claimable — silent mis-bucketing, the exact divergence fail-safe mode exists to prevent (and a v1 binary meeting an inbox/held `task.updated` halted as *malformed* — fail-safe, but misdiagnosed as garbage rather than as needing an upgrade). So `task.created` (status now a payload field) and `task.updated` (status value set expanded) both moved to **v2**; old binaries meeting v2 events enter read-only fail-safe with the honest "upgrade tuhdoo" message. The v1→v2 upcasters are the identity — a v1 `task.created` with no status field reads as `open`, and every v1 `task.updated` status is still valid — and are registered by construction in `core.NewReplayer`, so no replayer can forget them. Accepted consequence: once any peer's daemon writes a v2 event, every not-yet-upgraded peer goes read-only until upgraded — that is the T3 posture working, not a bug.

**Fail-safe, not best-effort.** When a daemon meets events it cannot honestly replay (unknown type from a newer peer, `v` above its comprehension), it enters **read-only degraded mode**: everything visible as of the last comprehensible state, writes and view regeneration paused, clear "upgrade tuhdoo" message. Best-effort skipping is rejected because it lets two teammates compute different truths from the same log and then write events based on divergent views — the "implicitly brittle" failure mode readmitted.

## T4. Daemon topology and transport

- **One daemon per repo** (not per machine). Repo-local state, config, locks, and sync loop; crash blast radius of one project; per-repo version pinning. A future per-machine supervisor / cross-project dashboard can *manage* per-repo daemons without reversing this. 
- **Endpoint:** Unix domain socket at `.git/tuhdoo/daemon.sock`, with `.git/tuhdoo/daemon.json` (pid, endpoint) for discovery — inside `.git`, never committed.
- **Protocols:** (1) **MCP via streamable HTTP** for harnesses; (2) a **plain JSON HTTP API** — same verbs, boring REST — for the CLI, the TUI, future UIs, and curl. All surfaces are projections of the same daemon state and cannot disagree.
- **stdio shim:** `tuhdoo mcp` proxies stdio ↔ daemon socket, so any harness config is just `command: tuhdoo, args: [mcp]`. The D7 principal is auto-derived at session bind *(revised 2026-07-30; originally `--as` was required)*: the shim takes the human half from git identity (the local part of `user.email`) and the daemon mints the agent half from the harness's MCP initialize `clientInfo.name` plus a per-daemon counter (`brandonbews/claude-code-3`), unique among the daemon's live sessions. `--as <principal>` remains as a full override for shared machines and scripted actors.
- **Principal override** *(added 2026-07-30)*: `git config tuhdoo.principal <name>` sets the preferred human principal once, replacing the `user.email` local-part rule everywhere auto-derivation applies — the mcp shim and the TUI's steer mode (motivation: GitHub noreply addresses derive to `4099114+brandonbews`). `--as` still beats it; the derived result passes the same validation (root principal only — the agent half stays daemon-minted), and a set-but-invalid value fails derivation loudly rather than silently falling back to email. **Storage is git config, not a file under `.git/tuhdoo/` and not the data branch**: a preferred name is per-human, per-clone state, so it does not belong in shared fleet state; git config gives one familiar command, per-machine reach via `--global` with ordinary precedence (local beats global), survival across `.git/tuhdoo/` wipes, and zero new file formats. Old events keep their recorded actors — identity derivation changes forward behavior only (T3).
- **Lifecycle:** lazy — first CLI/MCP invocation auto-spawns the daemon if absent (single instance via lockfile). No launchd/systemd ceremony. The daemon does not self-shutdown when idle (it is a few MB; cold starts cost more than it saves) and never exits silently — reason always logged.

## T5. MCP verb surface (v0) *(revised 2026-07-30 — out-of-band answers: `relay_answer` is the eleventh verb; revised 2026-07-31 — inbox/held arrived as fields, not verbs; revised 2026-08-02 — `get_backlog` grew the `scope` input: read parity, grilled 2026-08-01; revised 2026-08-04 — the confirmation gate: `confirm_claim` is the twelfth verb, `001` D6)*

Twelve tools *(originally ten; `relay_answer` added 2026-07-30, `confirm_claim` added 2026-08-04 — rationale below)*. Agents perform worse as tool count grows; every verb earns its slot. The D1 loop — claim → work → record → escalate — in minimum calls.

| Group | Verb | Notes |
|---|---|---|
| Orient | `get_backlog` | Ready-filtered, priority-ordered, dependency-aware — not a raw dump. *(2026-07-31)* Returns three arrays: `ready`, plus `inbox` and `held` (creation order) so agents orient on captured and paused work without ever being served it. *(2026-08-02)* An optional `scope` input adds the remaining sections on request — read-parity paragraph below. |
| Orient | `get_task` | One task fully hydrated: description, edges, notes, runs, escalations — start work in one call. |
| Loop | `claim_next` | **Atomic query-and-claim**: best ready task, claimed in one motion, optional capability/label filter. Kills the local browse-then-claim race; fewer tokens. |
| Loop | `claim_task` | Claim a specific task (the human-directed path). |
| Loop | `release_claim` | Voluntary stand-down, reason recorded. |
| Loop | `confirm_claim` | *(added 2026-08-04)* The D6 referee's gate: lands the claim's irrevocable `claim.confirmed` through the remote CAS, or answers that the attempt lost. Call before merging or arming auto-merge — a provisional claim is not proof of ownership; a confirmation is. |
| Loop | `finish_run` | Outcome + links (branch/PR/commits) + summary. Outcomes: `done` / `failed` / `abandoned` / **`blocked`** (waiting on an escalation answer — distinct from gave-up). *(2026-08-04)* `done` is refereed: the daemon runs the D6 confirmation gate inside every `done`-recording path and coerces a lost attempt to `superseded`, keeping the reported links as the salvage record. |
| Communicate | `escalate` | Question + context + blocking-or-not. |
| Communicate | `add_note` | Checkpoint observations (see agent protocol below). |
| Communicate | `relay_answer` | *(added 2026-07-30)* Record an out-of-band answer to an escalation — one given in the asking agent's live session rather than on a steering surface. Emits the same `escalation.answered` event as a TUI answer, so readiness unblocks identically. Semantics below. |
| Decompose | `create_task` | **Batch with intra-batch temp refs**: submit a whole DAG (epic + children + dependency edges) in one call using placeholder refs (`"tmp:setup-daemon"`); daemon assigns real IDs, resolves refs, commits atomically — whole plan lands or nothing does. Single task = batch of one. |
| Decompose | `update_task` | Status, priority, edges, labels. |

**Session-bound leases — no heartbeat verb.** While the MCP session holding a claim stays connected, the daemon auto-renews its leases. Session dies → renewals stop → lease expires → task returns to pool. The least reliable party (the agent) is never responsible for the most safety-critical bookkeeping. The daemon **auto-closes runs orphaned by lease expiry** as `outcome: interrupted` — never assume an agent's last act was tidy. *(2026-08-04)* The same posture covers race losers: a voided claim whose lease expires unclosed gets a synthesized branch-less `superseded` run, and a loser that does report gets its `finish_run` coerced to `superseded` with its links kept — `001` D6 carries the full mechanism.

**The confirmation gate rides the verbs, not a background process** *(2026-08-04, `001` D6)*. `confirm_claim` and every `done`-recording path run the gate synchronously: examine the remote head, push `claim.confirmed` onto exactly that head via the ref CAS, at most one confirmation per task by construction (the T2 app-level merge/push path refuses to carry a second). No remote configured: locally sound, instant. Remote configured but unreachable: honest retryable refusal, never a guess. Schema note (T3): `claim.confirmed` is a new event type — older binaries meeting one enter read-only fail-safe with the "upgrade tuhdoo" message; upgrade every machine before the gate ships events in a mixed fleet.

**Out-of-band answers: the relaying agent is the scribe, never the decider** *(2026-07-30)*. Escalations are often answered in the asking agent's own live session rather than on a steering surface; without a relay path the settled question lingers in the inbox, polluting exactly the signal escalations exist to provide. `relay_answer` records such an answer with honest attribution: the event's envelope actor is the relaying session's principal (the agent wrote the event), and an additive `answered_by` payload field on `escalation.answered` names the principal the answer is attributed to. The daemon derives `answered_by` as the session principal's root (D7) — it is never agent-supplied, so a session can only ever attribute an answer to its own root. Replay credits the answer to `answered_by` and, where that differs from the envelope actor, marks the answer as *relayed by* the actor; pre-existing events carry no `answered_by` and replay falls back to the envelope actor, so stored bytes stand untouched (T3, additive-first). Guard rails: the agent surface answers **open escalations only** — amending a settled answer stays human work on the steering surfaces, where last-answer-wins applies; **no claim on the task is required** — the blocking protocol has the asker release before any answer can land; **any session may relay** — restricting callers would be theater, since the trust boundary is repo write access (D4) and the attribution derivation is the real guard. The "human" in this section is today's answerer, not a type constraint: attribution binds to the session's root principal, whatever kind of actor that turns out to be.

**Inbox and held ride existing verbs — fields, not verbs** *(2026-07-31; status model in `001` D5)*. The verb count stays eleven: `create_task` items gained an optional `status` field accepting `open` (default), `inbox`, or `held` — creating directly into `held` is deliberately permitted (permissive by design: an agent decomposing work may legitimately park a child it has already triaged), while born-terminal creates (`done`/`cancelled`) are rejected as caller mistakes — and `update_task`'s `status` accepts all five values, which is the entire promote (`inbox`→`open`), pause, and resume (`open`↔`held`) surface. `claim_next` and `claim_task` never serve inbox or held tasks: `open` is the only claimable status, enforced in the core's readiness rule and tested explicitly on both claim paths. Title-only capture is a legitimate `create_task` call **for inbox items**; the tasks-are-prompts bar applies at promotion (agent-protocol doc).

**`get_backlog` scope: read parity as a field, not a verb** *(2026-08-02; grilled 2026-08-01)*. The MCP parity audit (2026-07-31) verified all ten write-side steering actions but left the read side blind: no MCP path listed in-progress, blocked, done, or cancelled tasks, or open escalations — a blocking escalation even removes its task from `ready`, so an MCP-only agent could not discover the very ID it needed for `get_task`, and `relay_answer` demanded escalation IDs no verb could produce. Settled: MCP must be **read-self-sufficient** — the CLI one-shots remain the scripting surface, not the excuse. The verb count stays eleven: `get_backlog` gains one optional `scope` input, an array of section names from `in_progress`, `blocked`, `done`, `cancelled`, `escalations` (plumbing vocabulary — `cancelled`, never "archived", matching `update_task`). Omitted or empty, the response is byte-identical to the three-array shape above — the worker hot path (`get_backlog` → `claim_next`) never pays a new token. Each requested name adds one response array keyed by that name; unknown names are rejected with a clear error, never ignored. **Slim rows are a design constraint, not an optimization**: every scope row carries `id`, `title`, `status`, `priority`, `labels`, and **no description** — orientation lists, hydration digs (`get_task`). Per-scope payoff fields: `in_progress` adds the holder principal and lease expiry; `blocked` adds waiting reasons condensed to `dep:<task-id>` / `esc:<escalation-id>` (the same condensation as the T7 one-shot contract — the story lives in `get_task`); `done` / `cancelled` add `closed_at` / `closed_by`, newest first (recency is the browse axis); `escalations` returns full open escalation records (id, task, question, context, blocking, raised_at) in raise order — not slim by design, the question text is the payload — and open only, because `relay_answer` serves open escalations only and answered ones hydrate via `get_task`.

**No delete, no admin verbs.** The ledger never deletes; `cancelled` is the archive. Curation (cancel, reprioritize, retitle, re-edge) is mechanically open to agents through `update_task` — the schema does not gate it. The norm that curation happens at a human's direction is protocol (`docs/agent-protocol.md`), not schema — the same permissive-mechanics/documented-semantics split as the status model. *(Rewritten 2026-08-02; the original "curation is human work via CLI/TUI" wording contradicted the 2026-07-31 parity-audit clarification above.)*

**The agent protocol doc is a first-class deliverable.** Findings from role-playing the primary user (a frontier-model agent):

- **The ledger is agent memory before it is human audit trail.** Sessions end and contexts compact; a fresh agent claiming a previously-attempted task resumes from prior runs and notes instead of re-deriving hours of investigation. *(Revised 2026-07-30, steering: continuity is carried by the typed transition events — claim, finish_run, release_claim, escalate, the synthesized interrupted run — whose payloads are already mandatory; `add_note` is optional mid-flight garnish, not the primary mechanism. The original "checkpoint noting … letters to the next incarnation" framing overstated it; the agent protocol doc carries the current doctrine.)*
- **Escalations are answered after the asking agent is gone — design for succession, not conversation.** The protocol: escalate → note exactly where work stopped → release the claim → `finish_run(blocked)`. The answer lands on the task; the next claimant picks up question-and-answer in hydration.
- **Task descriptions are prompts.** Output quality off `claim_next` is bounded by what's in the task: acceptance criteria, constraints, file pointers. In product (b), writing a good task *is* programming the fleet — a documentation/culture convention with more leverage than any schema feature.

## T6. Views: four, code-generated, version-stamped

Rendered to the data branch on every write/merge; audience is the **remote/browsing surface** (host web UI, teammates, posterity) — local humans use the CLI (T7), agents use MCP.

1. **`README.md`** (branch root) — orientation + live counts; the host renders it when anyone browses the branch. The "clone it and you can read it" soul made visible.
2. **`backlog.md`** — ready (priority order), claimed (by whom), blocked (on what); parent structure as nesting.
3. **`escalations.md`** — the steering inbox: open questions, who, which task, waiting how long.
4. **`tasks/<id>.md`** — per-task biography: description, edges, status history, notes, runs with links. `git log` on the file is the task's history for free.

Nothing else in v0. **No template engine** — plain Go functions building markdown, embedded in the binary: nobody edits templates in v0, determinism is the prime directive, and string-building Go is the most testable and author-reviewable form (byte-exact table-driven tests). User-customizable templates are a parked future feature.

**View-churn defense:** views carry a **view-format version** stamp (`views/.meta`); the rule is **highest version wins** — a daemon never overwrites views stamped by a newer generator; it updates the event log only and lets the newer peer regenerate. Prevents mixed-version regeneration ping-pong wars. Staleness consequence is cosmetic only (T3 table); replayed state (CLI/MCP/TUI) is always current.

## T7. Human surfaces: CLI portal in v0, TUI in v1, browser demoted *(revised 2026-07-30 by Cycle 4 — one verb-less TUI; revised 2026-07-31 — one-shot output is serialization, not design)*

The v0 CLI is not a thin setup veneer — it is the **local human's primary portal** (the author runs terminal-over-SSH; checking out a branch to read markdown is absurd, and a browser tab is friction where a tmux pane is native):

- `tuhdoo status` — one-screen fleet overview: active claims, open escalations, queue depth, sync state (`local-only` is a normal state).
- `tuhdoo backlog` / `tuhdoo task <id>` / `tuhdoo escalations` — terminal renderings served from the daemon's replayed state; always current. Scriptable, pipeable plumbing — deliberately untouched by the Cycle 4 revision *(and re-rendered 2026-07-31 as pure serialization — the contract block below)*.
- `tuhdoo create <title>` / `tuhdoo update <id>` / `tuhdoo answer <id> <text>` *(added 2026-07-31)* — the write path when no MCP session exists: shell humans who prefer commands to the TUI, scripts, cron jobs, and agents wrapping up after a deploy restart killed their session. They speak the same daemon HTTP API as TUI steer mode with the same actor rules (a root human principal: `--as` wins, else the `tuhdoo.principal` git config, else the `user.email` local part). Descriptions read from stdin via `--desc -`; list flags are full replacements; `answer` addresses an open escalation by its own ID or its task's ID, with the short-ID input contract throughout. **The claim lifecycle (claim / finish_run / release) is deliberately excluded**: leases are session-bound (T8) — a claim taken by a one-shot command would have nothing renewing it and would lapse interrupted. The MCP shim stays the only work-loop surface; the CLI help text owns this exclusion explicitly.

**One-shot output is serialization, not design** *(2026-07-31 grill cycle — supersedes the sectioned digest `tuhdoo backlog` / `tuhdoo escalations` rendered until now)*: run bare, the read commands had grown a designed digest — sections, counts, waiting-prose — a fossilized older cousin of the TUI: a second look at the same information that had to be maintained, and that every TUI grill had to rule around ("one-shot output untouched" clauses, twice on 2026-07-31 alone). The functionality stays; the second *look* dies. The CLI surface is governed by two rules plus an output contract:

1. **Steering parity.** Steering capabilities — read state, shape the backlog, create/update/answer — ship in both TUI and one-shot CLI form. A steering feature added to one without the other is a decision someone must make explicitly, not drift.
2. **The work loop is session-only.** `claim` / `finish_run` / `release` are never one-shot commands: leases renew only while a live MCP session holds them (T5, T8), and a claim taken by a one-shot would have nothing renewing it and lapse `interrupted`. The help text has owned this line since the write commands landed; it is hereby promoted to design record.

**The output contract:** one-shot output is serialization, not design — stable, plain, line-oriented; it changes when the data model changes, never because the TUI was redesigned. No future TUI design decision owes the one-shots a clause. Concretely, `backlog` and `escalations` emit a header row plus one aligned record per line — the kubectl-get / git-branch -v register: readable to an eye, trivial for grep, zero opinions. A STATE column replaces section headers (`tuhdoo backlog | grep ready` selects exactly the ready rows); blocked waiting-reasons condense to IDs, never prose (`dep:<task-id>`, `esc:<escalation-id>` — the story lives in `tuhdoo task <id>`); empty cells render `-` so every column is present on every row; and there is **no ANSI styling at all**, which also deletes the TTY-vs-pipe degradation surface for these two commands — the bytes are identical either way. Status words survive as column values, hyphenated where two words must stay one grep/awk token: `ready`, `in-progress`, `blocked`, `on-hold`, `inbox`, `done`, `cancelled` *(so revised 2026-08-01: `archived` became `cancelled` with the status-vocabulary revision below; `on-hold` survives as the sanctioned display token for `held`)*. Full IDs throughout, as ever — scriptable plumbing keeps full IDs. `status` and `task <id>` sit under the same two rules and the contract's spirit, but reshaping their output is a separate capture; nothing here changes them. (The committed markdown views of T6 are a different surface with their own contract — untouched.)

**The interactive surface is a single verb-less TUI** *(Cycle 4, 2026-07-30 — supersedes the v0 `watch` command and the v1 `tuhdoo top` name; both shipped, briefly coexisted as duplicate Bubble Tea models, and are now tombstoned)*. **Bare `tuhdoo`** launches the steering TUI (Bubble Tea, same binary), guarded: it launches only when stdout is a TTY — otherwise usage prints, exactly as bare invocation always behaved, so pipes/scripts/CI never meet a TUI — and an uninitialized repo gets a `run tuhdoo init` hint. `-w`/`--watch` launches the same screen **disarmed**: steering keys dead, navigation and the task detail screen alive, a visible `watch mode` badge in the header. The mode is fixed at launch — no keypress can re-arm a disarmed pane. Watch mode needs no principal; steer mode derives one from git identity as before (`--as` overrides; combining `--as` with `--watch` is rejected).

One screen carries the whole picture: a header (mode badge, sync line, counts), four status sections (open escalations, ready, in progress, blocked — with `waiting:` reasons) *(2026-07-30: the escalations section renders under the title "Needs Input" — the entity keeps its name everywhere; the header alone softens the severity the word overstates, and deliberately avoids naming who answers, since a future answerer may not be a human)*, flat rows with edge-marker suffixes (`· N deps`, `· in <parent>` — tree rendering is gated on the edge-semantics open question), and an in-place task detail screen (enter: description plus full ULID-merged history, live off the polled snapshot) — read-only this round; arming it is a filed follow-up. Key semantics are absolute: `esc` steps out, `q` quits, `ctrl+c` quits — one meaning per key, on every screen.

**Short IDs are the human contract** *(2026-07-30; revised 2026-08-02 by the ID-disparity grill — the full ULID leaves the TUI)*: the git model, applied to task IDs — the full ULID is plumbing, the short form (`t-` + lowercase last four of the ULID tail, e.g. `t-d83w`) is what humans see and type. Canonical IDs remain ULIDs (sequential IDs would need the central counter the no-server design forbids, and ULID sort order is load-bearing); this is display and input sugar only — stored bytes, events, the HTTP API, and the MCP verbs are untouched (agents pass full IDs from hydration JSON and never retype them). Display: every task reference in the TUI uses the short form — including the detail screen's `id` line, which shows the short form dimmed *(so revised 2026-08-02; this line previously kept the full ULID exactly once as the copyable canonical form, and was the last full-ID surface humans saw)*. The full ULID has no TUI surface: the fragment resolver makes the short form a complete key for every human entry point (`tuhdoo task` / `update` / `answer` / `--parents` / `--depends-on` all resolve fragments), and when a human genuinely needs the full form — cross-referencing an event filename or a `tasks/*.md` path — one-shot `tuhdoo task tuh-xxxx` prints it. **Accepted consequence** *(2026-08-02)*: short-tail ambiguity grows with total task count (~38% chance some pair of tasks shares a 4-char tail by ~1,000 tasks); the resolver already handles collisions loudly — ambiguity is an error listing the candidates — and the working-set-retirement open question (Cycle 4), if built, bounds the pool at working-set size. Dep/parent references that resolve in the snapshot are annotated with status and title (`depends on t-d83w (done — old chore)`) — done/cancelled tasks render no rows, so the annotation is what proves such an edge isn't dangling; unresolvable IDs render bare, never an invented status. Input: `tuhdoo task <id>` accepts a full ID, the short form, or any unambiguous ID fragment; ambiguity is an error listing the candidates. One-shot command output stays byte-identical — scriptable plumbing keeps full IDs.

**The ID prefix carries the brand: `tuh-`** *(2026-07-31, dogfood steering decision — extends the short-ID contract above)*: a prefix must exist for ID shape, so the letters should carry brand, and the brand metric is distinctiveness — `tuh-` is uniquely tuhdoo (`td-` reads as generic todo and collides with HTML `<td>`; no prefix loses the ID shape). New tasks mint with `tuh-`; task IDs minted before this date carry `t-` and are **never rewritten** (T3) — no migration, mint-forward only — so a mixed-prefix window exists and simply ages out of view at dogfood pace. Every surface derives the prefix from the ID itself (everything through the first hyphen), so both eras coexist without special cases: short forms follow the ID's own prefix (`tuh-d83w` for new tasks, `t-d83w` for old ones, side by side), and no code path validates or rejects either prefix. Cross-prefix input rule: a fragment's prefix is matched literally against the ID — `t-d83w` and `tuh-d83w` are distinct inputs that can never name each other's era — while a bare fragment (`d83w`) matches both eras and reports ambiguity when tails collide, per the standard resolution rules.

**One status vocabulary: the displayed words are the stored words** *(2026-08-01, dogfood datashape session — supersedes, in place, the 2026-07-31 "archive is the porcelain word for `task.cancelled`" decision that previously lived in this paragraph)*: the archive vocabulary is retired; a status has one word, and it is the stored one — `open`, `inbox`, `held`, `done`, `cancelled` — with exactly two sanctioned display exceptions: `held` renders as **"on hold"** ("held" alone confuses as a human-facing word; the mapping is defined in exactly one place in code — see the shelves paragraph below), and **NEEDS INPUT** names the open-escalations section (2026-07-30, unchanged). Concretely: cancelled tasks render as `cancelled` wherever a status appears (one-shot STATE column and tallies, the task-biography status line, edge annotations like `(cancelled — title)`, the committed markdown views); the TUI key is `c cancel` with confirm copy still ending "history stays on the ledger" and a `cancelled <id>` status message; `tuhdoo update --status` documents `cancelled` and the `archived` input alias is deleted. Rationale for un-accepting the one-day-old archive decision: "archived" collided semantically with `done` — both terminal, both kept forever, rendered as sibling sections — and the display mapping had already metastasized into two copied `humanStatus` functions plus a reverse input alias; the dual vocabulary cost more than the softer word earned. The 2026-07-31 worry that "cancel" reads as deletion is carried by the confirm copy ("history stays on the ledger") instead of by a vocabulary fork; the old objection that the `c` key "read as cancel, not archive" dissolves — the verb now *is* cancel.

**The shelves and quick capture** *(2026-07-31, with the D5 status-model revision)*: the dashboard grew two dim sections at the bottom — **ON HOLD above INBOX** (held passed triage, so it sits closer to workable; the display word for the `held` status is **"on hold"** — decided 2026-07-31, and since 2026-08-01 the *only* sanctioned status display mapping (status-vocabulary revision above): the stored value, API/flag vocabulary, and event bytes stay `held`, humans read "on hold", and the mapping is defined in exactly one place in code) — with reverse-dim bars *(revised 2026-08-04, TUI bar-recolors task: the shelf bars diverged — ON HOLD carries the dark-gray bar of the 2026-08-03 chrome hierarchy, and INBOX carries a black-on-bright-white bar, still 16-color; both sections' rows stay dim)* and dim rows: parked and captured work is visible without claiming the eye. Shelf rows are ordinary rows: enter opens the detail biography, `c` cancels (which is what makes cheap capture reversible), and a task blocked on an inbox/held dependency names that status in its `waiting:` reason through the existing edge annotation (`depends on tuh-xxxx (inbox — title)`). **Quick capture: `i`** opens a single-line input whose enter creates a title-only inbox item as the steering actor — y/n-free by design (capture must cost one keystroke and a title; cancel is the undo), armed mode only and fully absent in `--watch` (the key is dead and no bar or footer advertises it). **The TUI deliberately has no promotion key**: promotion is where the tasks-are-prompts bar applies, which means writing a real description — an agent/CLI conversation, not a single-keystroke temptation. One-shot surfaces follow: `tuhdoo backlog` renders On hold and Inbox sections (dim, same order) *(superseded 2026-07-31, later the same day: under the serialization contract above these are the `on-hold` and `inbox` STATE values, not sections)*, `status` counts them, `create --status inbox|held` and `update --status open|inbox|held` are the CLI capture and promote/pause/resume paths.

**Mouse: click selects, click again acts as enter** *(2026-07-31, dogfood steering feedback)*: the TUI tracks the mouse (Bubble Tea cell-motion tracking). A single click moves the cursor to the row under the pointer — hit-testing replays the exact rendered layout (same header, same variable-height row chunks, same cursor-following window), so it cannot drift from what is on screen — and a click on the already-selected row triggers exactly what enter does there; a double-click is the same thing by construction (the first press selects, the second finds the row selected). The wheel moves the list cursor and scrolls the detail screen; input modes ignore the mouse entirely. **Accepted consequence:** mouse tracking captures the pointer, so terminal-native text selection needs shift-click while the TUI runs — a real cost over SSH/tmux. **Mitigation:** tracking is armed-only — watch mode, the pane left open to read and copy from, never enables it and keeps plain click-drag selection; the model-level guard holds regardless (a click in a disarmed pane could only select and open the read-only detail, never input).

Accepted consequences (Cycle 4): the always-open pane is armed unless launched with `--watch` (mitigations: the flag, and cancel — `c cancel`, restored 2026-08-01 after a one-day detour through "archive" — stays confirm-gated); no runtime arm/disarm toggle — fluidity traded for an ironclad read-only guarantee; `watch` and `top` die as verbs with tombstone errors, not aliases — vestigial names outlive their excuse otherwise.

Rationale unchanged from v1's original TUI bet: works over SSH and in tmux where the author actually lives; Go's TUI ecosystem is best-in-class (retroactively reinforcing T1); and the steering scope (inbox, ledger, queue) is naturally a dense terminal dashboard. **Browser UI is demoted to v2+** — it's the kanban board that wants a browser, and the board stays banned until the steering loop is proven (D8). CLI, TUI, and any future web UI all speak the same daemon HTTP API; nothing is throwaway.

## T8. Cadence defaults

Config-file knobs; these are starting values, and the daemon logs collision counts and sync latencies so tuning is evidence-based.

| Knob | Default | Rationale |
|---|---|---|
| Commit debounce | 2s | Batch a fleet's burst into one commit; the TUI still feels live. |
| Push | Immediate for commits containing claims or escalations; else piggyback ≤ 30s | Claims race (D6); escalations have a human waiting. Notes can amble. |
| Fetch interval | 60s | With eager claim-push, worst-case collision window ≈ 1 min; D6 accepts rare duplicates. Host webhooks could make this push-driven later (optional add-on per T2). |
| Lease TTL / renewal | 15 min / every 5 min | Renewal is the daemon's job (session-bound), so short TTLs cost nothing; crashed fleets return tasks in ≤ 15 min. Three missed renewals = expiry. *(Supersedes the ~30 min sketch in D6.)* |
| MCP session keepalive | Ping every 30s; 3 failures tolerated | Session liveness is what lease renewal hangs off (T5), so the daemon probes it directly; three tolerated failures mirrors the lease posture above — a transiently slow client is not a vanished one. *(Added with B9; pings ride streamable HTTP's standalone GET stream, which is why agent access is shim-only — see `docs/agent-protocol.md`.)* |
| Confirmation gate | Synchronous push + fetch at confirm/finish; 5–30 s budget | *(Added 2026-08-04, `001` D6.)* The one deliberately synchronous sync in the system: accuracy outranks latency at the merge/finish moment. Idempotent — an already-confirmed claim answers instantly. Push contention retries ride the existing Cycle loop and count toward the collision telemetry. |
| Idle shutdown | None | Cold-start latency isn't worth a few MB. Exits are always logged with reason. |
